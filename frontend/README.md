# Phanda -- Web

Installable PWA for Phanda, a South African youth employment platform. This
build covers the landing page, auth (register/login), the optional
profile-building and CV-upload flow, and a home shell -- not the job
listings/apply/track screens, which are a separate pass. See "What's not
built yet" below.

Sibling repo to the FastAPI backend (`Phandas`) and the Android app
(`phanda-android`); this repo does not depend on either at build time, only
on the backend being reachable over HTTP at runtime.

## Stack

Vite + React + TypeScript + Tailwind CSS v4 + Zustand + React Router,
`vite-plugin-pwa` for installability. No Next.js, no alternate bundler.

## Setup

```bash
npm install
cp .env.example .env
```

Edit `.env` and set `VITE_API_BASE_URL` to your backend's address (see
below for testing on a physical phone).

```bash
npm run dev      # http://localhost:5173
npm run build    # outputs to dist/
npm run preview  # serve the production build locally
```

## Pointing at the backend

`VITE_API_BASE_URL` must include a trailing slash. For a browser on the same
machine as the backend, `http://localhost:8000/` is fine. **For a physical
phone on the same Wi-Fi**, `localhost` resolves to the phone itself, not your
computer -- use your computer's LAN IP instead:

```bash
# Windows
ipconfig | findstr IPv4
```

```env
VITE_API_BASE_URL=http://192.168.1.23:8000/
```

Windows Firewall may need an inbound rule for the backend's port before a
phone on the same network can reach it.

## Installability

- `public/icons/` holds the manifest icons (192, 512, a maskable 512, and a
  180 apple-touch-icon), generated by `scripts/generate-icons.mjs` -- a
  small script that writes raw PNG bytes with Node's built-in `zlib` rather
  than pulling in an image-processing dependency for four small brand-mark
  icons. Re-run it if the mark ever changes.
- The manifest (name, short_name, `display: standalone`, `theme_color:
  #0B8F55`, icons) is declared in `vite.config.ts` via `vite-plugin-pwa`,
  which also generates and registers the service worker
  (`registerType: "autoUpdate"`) via Workbox.
- The **Install app** affordance is a real, visible button (`InstallButton`)
  in both the landing page hero and the authenticated header -- not just a
  manifest sitting there unused. On Chrome/Edge/Samsung Internet it triggers
  the native install prompt; iOS Safari has no such API, so there it shows
  the manual "Share -> Add to Home Screen" steps instead.
- Verified: `npm run build` emits `dist/manifest.webmanifest` and
  `dist/sw.js`; Chrome's Lighthouse PWA audit (or DevTools > Application >
  Manifest) against `npm run preview`'s output confirms installability.

The service worker precaches the app shell only (JS/CSS/fonts/icons). API
responses -- listings, profile state, auth -- are never cached by it: stale
data served offline would be actively misleading for something like "is my
CV ready yet."

## Auth token handling

**Access token**: kept in memory only (`src/lib/tokenStorage.ts`), never
written to any Web Storage. It's gone on tab close or reload, which shrinks
the window an XSS payload has to read it.

**Refresh token**: stored in `localStorage`. This is deliberate, not an
oversight, and it's worth being upfront that it's a real tradeoff:

1. The backend returns the refresh token in the JSON response body, not as
   an `httpOnly` cookie. Browser JS necessarily holds the raw token at least
   once -- there's no storage location hidden from a successful XSS payload,
   because the payload runs in the same context that received the token in
   the first place.
2. Given that, `localStorage` vs `sessionStorage` vs IndexedDB isn't a
   security decision, it's a persistence one -- all three are equally
   readable by injected script. `sessionStorage` would force a full
   re-login every time an installed PWA is closed and reopened, undercutting
   a real point of installing it.
3. The backend's single-use rotation bounds the damage: a stolen token is
   good for one use (or reuse within its ~30s grace window -- verified
   against the live backend) before further reuse revokes the whole session.

**The actual fix** -- flagged here rather than silently worked around --
is the backend issuing the refresh token as an `httpOnly`, `Secure`,
`SameSite=strict` cookie instead of a JSON field, with CSRF protection on
the refresh endpoint. That's a backend contract change this client can't
retrofit.

**Single-flight refresh** (`src/lib/api.ts`): when a request gets a 401, it
awaits a single shared `refreshPromise` rather than firing its own refresh
call. Concurrent 401s from several in-flight requests all await the *same*
promise instead of each starting a new refresh with the same (about to be
invalidated) token. Unlike a multi-threaded client, no explicit lock is
needed for this: JavaScript's single-threaded event loop means the "is a
refresh already in flight?" check and "start one" write happen in the same
synchronous tick, with no `await` in between where a second caller could
interleave -- the event loop itself serialises it. `src/lib/sessionEvents.ts`
adds a one-shot guard so a hard refresh failure signals "session expired"
exactly once, no matter how many queued requests were waiting on it.

## Project structure

```
src/
  lib/            api client (single-flight refresh), token storage, error type
  store/          authStore.ts -- session state, register/login/logout
  hooks/          useInstallPrompt.ts
  components/     shared UI: Button, TextField, AuthLayout, InstallButton, icons
  pages/          Landing, Register, Login, Home
  features/
    onboarding/   ProfileWizard (skippable, 4 steps), CvUpload (polls for status)
  types/api.ts    backend contract types
scripts/
  generate-icons.mjs   one-time PWA icon generator
```

## What's not built yet

Deliberately out of scope for this pass: job listing search, matching
results, applying to a listing, and application tracking. The home shell
exists only to prove the signed-in state and the empty/partial-profile
states work; it does not yet show real listings. That's the next pass.
